# Reading the report

Every run writes one report, and this page tours it section by section so you know what each part is telling you and what to do about it. The report is Markdown on stdout, and the same content as JSON (`--json`) and as a self-contained HTML page (`--html`) when asked. The example tables below are what the renderer prints for a small constructed run (one claim carried, one contradicted, one dropped), so every column appears once; the [README](../README.md#a-real-example) quotes a report from a real model run.

## The sections, in order

The report has seven sections, and four more on a `merge` run. The last of the four is printed only when the merge declared an addition, which is possible at `open` and at `sourced` and at no level below them. One more, **Attributions**, follows Findings on either command and is printed only when the merged document credits a statement to a source that does not state it.

**Verdict** - one line, matching the exit code.

**Coverage** - the denominators, before the findings: how many claims were extracted from each document, how many were verified, how many errored, and how many pieces of evidence were grounded. It comes first because a check that examined nothing passes, and from its output that is indistinguishable from a check that examined everything and found no fault. Errored units leave the denominator and are counted on their own line, so coverage reads `74/76 (2 errored)` and never `74/81`. Each direction also gets a row counting the claims carried only in part, printed even when it is zero: they are not in the numerator above it, and without a row of their own that ratio would read as whole claims lost.

A source that decomposes to **no claims at all** was not examined at the claim level, and the report says so rather than reporting a clean verdict over it. On `verify` that is an error and exits 2: the claim level is the whole examination there, so coverage for that source is unestablished. On `merge` it exits as it otherwise would, because the reconciler still checks the source structurally, and the report says coverage for it rests on that check alone.

The forward figure is then repeated **once per source, against that source's own claims**. The pooled ratio cannot tell a merge that lost a claim from each of two sources from one that ignored a source completely (both read `2/4`), and those are different failures. A source that yielded no claims says so in words rather than scoring `0/0`. The per-source rows move no exit code: every claim they count is already a finding, arranged here so the shape of the loss is visible.

**Findings** - one entry per claim that was dropped, contradicted, invented, or carried only in part: the claim text, the file and line it came from, the verdict, the span the model quoted, and whether that span was grounded. Each of the five classes has its own heading, and a partial is never filed under the whole-claim failure next to it. Nothing is summarised away; the finding list is the evidence. One thing is *moved* rather than summarised: a dropped claim the merge declared and the forward pass confirmed is listed in the review queue below instead.

**A finding that has two sides to compare shows both, stacked**, wherever the reconciler holds both strings: a reworded structural finding takes the source segment and the merge segment it most resembles, a false departure takes the segment and the replacement declared for it. Three lines: the source text, the merge text, and a word diff between them in `wdiff`'s notation, `[-was-] {+is+}`, marking what changed inside a run of characters rather than the smaller number of whole words that changed. Below 0.8 similarity a word diff marks nearly every word twice and is harder to read than the two texts plain, so only the pair is printed there. Every surface renders the same three lines (the Markdown report in a fence, the HTML report and the page in their own monospaced block), so you never have to go and find both texts by hand.

When this section is empty and **Structure** or **Attributions** is not, it says so and points there, so a verdict line that opened `1 finding(s)` is never followed by a bare `None.`

**Attributions** - every sentence in the merged document that credits a named source with a statement that source does not contain, while another source contains it word for word: "According to the Operator Guide, the minimum TLS version is 1.2" over an Operator Guide that never mentions TLS. The fact is real and the attribution is invented, so no claim-level check can see it: the decomposer reads "the guide states X" as a claim about X, which is right for almost every attributed sentence and is exactly what hides this one. So this is matched on the texts and asks no model, which is also why it runs at `--verify-depth coverage`, where nothing else reads the merged document back. It is bounded on purpose: a name has to match one source's title, a separated part of it or its filename; a sentence a source already carries as written is never listed; and a statement no source contains, or one reworded past a word-for-word match, is left to the other checks rather than guessed at. A finding here is a document fault and exits 1.

**Length capped** - every `reason`, `replacement` or `rationale` a model wrote past its length cap. A length violation is not fatal: the field is capped in place (a `replacement` two-ended, by its first and last characters; a `reason` or `rationale` cut hard), and the document and the record naming it both survive. Nothing here moves the exit code: this reports what the parser had to shorten before Structure's or Findings' checks ran, not a fault in the merge or the verdict.

**Not graded** - every claim the tool refused to grade, and why. When a verify batch comes back malformed and the repair attempt does not fix it, the fault is usually in one record rather than in the answer as a whole: a `MISSING` verdict that also quotes an evidence span, say, is unusable while every other record beside it is fine. Those records are dropped by name and the rest of the batch is graded, instead of the whole batch being thrown away. This never improves the exit code. A run with anything in this section exits 2 and says so in the verdict line: the claims listed here have no verdict in either direction, so the report is incomplete and cannot be read as a pass.

**Inventory** - every claim that was extracted, carried or not, one table per document. The sections above are the exceptions; this is the whole. Findings answer *what went wrong*, but someone merging two knowledge-base articles usually wants to know what happened to one particular fact, and an exception-only report answers that only by silence, the same silence it prints when nothing was examined at all.

### `notes-a.md` -- 3 claim(s): 1 dropped, 1 contradicted, 0 partly kept, 1 carried

Each claim below was read against `merged.md`.

| # | Claim | Line | Status | Note |
|---|---|---|---|---|
| 3 | The archive is signed. | 3 | dropped | The reference text settles it. |
| 2 | The connect timeout is 30 seconds. | 2 | contradicted | 'The connect timeout is 60 seconds.' in `merged.md` -- The reference text settles it. |
| 1 | The relay listens on port 8443. | 1 | carried | 'The relay listens on port 8443.' in `merged.md` -- The reference text settles it. |

Claim text is reproduced whole. It is never shortened to fit the column, because a claim bundling three facts can be scored covered by a merge that dropped one of them, and an abbreviated claim would hide exactly that half. The cell wraps instead. A line number the model estimated rather than a span the anchor found is printed `12 (unverified)`, and a quote `verify` could not ground is marked in the row it sits in, so an ungrounded quote never reads as a checked one. The Note column is filled on carried rows too: a blank note beside *carried* cannot be told from a claim nobody looked at.

Then the reverse, over the merged document's own claims, which is where a merge that carried every source fact and also asserted something no source does becomes visible:

### `merged.md` -- 3 claim(s): 0 invented, 1 contradicted, 0 supported in part, 2 supported

Each claim below was read against `notes-a.md` and `notes-b.md`.

| # | Claim | Status | Found in | Note |
|---|---|---|---|---|
| 2 | The connect timeout is 60 seconds. | contradicted | `notes-a.md` | 'The connect timeout is 30 seconds.' in `notes-a.md` -- The reference text settles it. |
| 1 | The relay listens on port 8443. | supported | `notes-a.md` | 'The relay listens on port 8443.' in `notes-a.md` -- The reference text settles it. |
| 3 | The read timeout is 45 seconds. | supported | `notes-b.md` | 'The read timeout is 45 seconds.' in `notes-b.md` -- The reference text settles it. |

An invented claim is sourced to `--` rather than to the file the model named, because it is in no source and printing one would have the report invent a provenance for the invention. Every count in every heading is counted by code from the rows printed under it, and held against the coverage table above: two figures for one quantity is the defect this report exists to refuse, so they are asserted equal, and a run where they disagree comes back inconclusive instead of printing both.

## The sections on a `merge` run

**Structure** - no model is asked anything to produce it. Nine mechanical checks over the source texts, the merged document and what the merge declared about it: every one of them is a set difference, a string containment or a division, so you can check any entry by hand. They cover what the claim passes cannot: `prompts/decompose.md` is told to skip headings, formatting and boilerplate, so a merged document that dropped both titles, moved a digit inside a fenced block or left a whole source segment out produces no claim to lose and no verdict to fail. Findings here move the exit code exactly as claim findings do, and are counted beside them in the verdict line rather than merged into them: a model's judgement about one claim and a token that did not survive are different kinds of evidence. The count of checks and the number of segments they ran over are printed above the result, and a run where the reconciler did not run says **Not checked** rather than reporting no findings: an examination that did not happen is not a clean one.

One of those nine checks needs its rule spelled out, because "unchanged" means two things. An invariant-core token (inline code, a numeral, a version string, a path, a link destination) is checked against the merged document with runs of whitespace collapsed, since in prose a run of spaces is not content and a line wrap is not a change. A fenced code block is checked with its interior whitespace intact, byte for byte up to line endings and trailing spaces. It is the same rule over two kinds of text: inside a fence, whitespace is content, and re-indenting a YAML block from four spaces to two changes what it means.

**Review queue** - the losses the merge owned: claims that came out of a segment the merge declared dropped, where the forward pass agrees they are gone. Each entry answers the question the reader actually has: what was left out, which segment it was left out of, what the merge said about leaving it out (its own sentence, quoted and not graded), and, last, that the absence was confirmed by the forward pass rather than taken on the merge's word. A finding is something that went wrong; a queue entry is a decision somebody made and recorded, and your job is to agree with it or put the fact back. Nothing here moves the exit code, with one exception printed in this section when it fires: past 3% of the source segments declared dropped, the volume is a finding of its own and the run exits 1. Without that ceiling the queue would be a way of declaring your way to a clean exit. An empty queue says so; it is not omitted.

**Declarations** - the merge writes a record for every source segment it did not carry over word for word, saying which of *reworded*, *superseded*, *subsumed*, *duplicate* or *dropped* happened to it. This section holds each record against the forward verdicts on the claims that came out of that segment, and marks it confirmed, rejected, or unchecked. The reason the merge wrote is printed in a column of its own, beside and never mixed into the tool's account of how the grade was reached: one is the merge arguing for itself and the other is the arithmetic checking it, and you have to be able to tell which you are reading. Unchecked is its own outcome and not a pass: plenty of segments produce no claim at all, and a declaration nothing examined has not been agreed with. A rejected declaration is the merge describing itself wrongly, which is not the same as a lost fact: it is reported here and does not move the exit code, and it excuses nothing. A claim the forward pass found missing under a rejected declaration is a finding, not a queue entry. A merge that declared nothing says so out loud, because silence is itself the claim that every source segment survived character for character.

**Added from outside the documents** - printed only when the merge declared one. At `open` and at `sourced` the merge may state something neither document contains, and it does so by writing a record rather than a sentence: the statement, what it *corrects* if it replaces something a document states, the *basis* it rests on (`citation` or `own-knowledge`, a closed choice and not a free field), the *source* where a citation is one, the merge's own reason, and which extracted claims the statement covers. This tool resolves nothing and fetches nothing, so `Source` is printed as text and never as a link: a link the report drew would read as a destination the report had been to. A statement the documents are merely *silent* about is excused by the declaration and moves no exit code: the sources cannot deny it, and the record makes it reviewable. A statement that *corrects* one is the other case: the merged document now asserts something a source denies, nothing here can tell a correction from a corruption, and so it stays a finding and still exits 1. The section says which of the two each row is, where you meet the row.

## Provenance

**Provenance** - run mode, endpoint, model id per role, structured-output tier and how it was chosen, temperature, seed, which roles were allowed to reason, the LLossless commit, call and token counts, a digest per prompt, and a UTC timestamp. On a run whose model was granted a web tool there is one row more: which tool, and whether the turn counter saw it used. The grant is also noted under the table, because a query or a fetch the model makes can carry text from the documents being merged to a third party, while LLossless itself still opens no socket.

Two of those rows say less than they look like they do, both deliberately. The prompt digest is over the *composed* text (the base file plus whichever fragments that call included), so it is not the sha256 of any file on disk and cannot be reproduced with `sha256sum prompts/merge.md`; it identifies what was sent, which is what a recording has to be keyed on. The endpoint row prints an opaque id rather than an address whenever the run is labelled, so two records can be told apart as same-machine or not without an address appearing anywhere.

The provenance block records the endpoint **host only**, never the full URL, which can carry a deployment path or a token in a query string. And when the endpoint is not local it prints a warning saying in plain words that document content left the machine, because a local-first tool that goes remote quietly is worse than one that never claimed to be local.

**One gap:** the report does not yet record the model's **quantisation**. Reading it needs no new call: `/api/ps`, which the tool already asks for the served context window, returns `details.quantization_level` in the same response, and the window probe keeps it. What is missing is the step from there into the report. The quantisation of the reference configuration is the hand-maintained line in [the measured results](results.md#reference-configuration) instead.
